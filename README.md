# prozorro-check

«Прозорро Монітор»: бот шукає підозрілі тендери на Prozorro і скидає чернетки мені в Telegram. Що схвалю, те йде в X (посиланням, я тисну Post сам) і в телеграм-канал.

Прапорець - це привід подивитися уважніше, а не доказ порушення.

## Як працює

Дві частини:

- **GitHub Actions** (`prozorro-bot`, раз на 30 хв) - лише аналітика. `prozorro_monitor.py` тягне нові тендери з API Prozorro у SQLite і рахує прапорці, `prozorro_patterns.py` шукає закономірності, `prozorro_history.py` - історію постачальників, `prozorro/pipeline.py` пише тексти й надсилає чернетки у Worker. Telegram тут не чіпаємо.
- **Cloudflare Worker** (`worker/`, безкоштовний тариф) - усе, що стосується Telegram, і єдине сховище чернеток та рішень (база D1). Натискання приходять у Worker одразу (вебхук), він зберігає рішення, відповідає на кнопку й пише кожне натискання в журнал подій. Раз на 10 хв: публікація в канал, закріплений «Розклад», тижневий підсумок.

База тендерів лежить у кеші Actions і потрібна лише для аналітики: якщо кеш зникне, тендери завантажаться знову, а чернетки й рішення в D1 нікуди не дінуться. Резервна копія всього з D1 (`state/backup.json`) і файли моделі зберігаються в окремій гілці `bot-state`: один коміт, який бот перезаписує щопроходу, тож історія `main` лишається чистою.

## Перевірка в Telegram

- У чаті одночасно до 8 чернеток (`REVIEW_WINDOW`). Щойно я вирішую одну, приходить наступна: спершу ті, де більше грошей під ризиком.
- ✅ Опублікувати - чернетка тут же стає дописом для X з кнопкою «Відкрити в X» (#ready_to_x), а в канал вона піде у свою чергу. Коли запостите в X, натисніть «✔️ Опубліковано в X» - повідомлення зникне з чату.
- ✏️ Редагувати - бот просить новий текст відповіддю (reply). `+link` наприкінці додає посилання на тендер.
- ❌ Відхилити - чернетка зникає з чату.
- ⏭ Пізніше - назад у чергу, покажеться після інших.
- Чернетка без рішення 30 днів (`EXPIRE_DAYS`) прострочується. Ті, що висять у чаті ~44 год, бот надсилає заново (Telegram дає видаляти повідомлення лише 48 год).
- Команди: `/queue` - стан черги (заодно перевіряє, чи чернетки справді в чаті; видалені вручну надсилаються знову), `/next` - ще порція чернеток (навіть якщо в чаті вже 8), `/pause` і `/resume` - публікація в канал.
- Канал: по одному допису раз на годину, тихі години 23:00-08:00 за Києвом. Що й коли вийде - у закріпленому «Розкладі».
- Щонеділі з 18:00 - статистика тижня мені й підсумки тижня в канал.

## Перше налаштування Worker

1. Зареєструватися на [cloudflare.com](https://dash.cloudflare.com/sign-up) (безкоштовно). Один раз відкрити **Workers & Pages**, щоб створився піддомен `*.workers.dev`.
2. **Account ID**: Workers & Pages, праворуч (або в адресі `dash.cloudflare.com/<account id>/...`).
3. **API token**: My Profile → API Tokens → Create Token → шаблон **Edit Cloudflare Workers** → додати рядок дозволу **Account · D1 · Edit** → Continue → Create Token. Скопіювати токен.
4. GitHub: Settings → Secrets and variables → Actions → New repository secret: `CLOUDFLARE_API_TOKEN` і `CLOUDFLARE_ACCOUNT_ID`.
5. Actions → **worker-deploy** → Run workflow. Він створить базу, розгорне Worker, задасть секрети, увімкне вебхук, перенесе старий журнал (`state/ledger.json`) і закомітить адресу Worker у `worker/url.txt`.
6. На cron-job.org видалити завдання для `prozorro-telegram` (такого workflow більше немає). Завдання для `prozorro-bot` лишити.

Потім worker-deploy запускається сам після кожної зміни в `worker/`.

**X через API (необов'язково).** Якщо додати в секрети репозиторію всі чотири ключі `X_API_KEY`, `X_API_SECRET`, `X_ACCESS_TOKEN`, `X_ACCESS_SECRET` (developer.x.com → застосунок із правами Read and write → Keys and tokens) і знову запустити worker-deploy, бот публікуватиме схвалене в X сам: на найближчому проході, поза тихими годинами, а в повідомленні з'явиться посилання на допис. Інтервал і добовий ліміт - `X_MINUTES` і `X_MAX_PER_DAY` у `worker/wrangler.toml`. Без ключів - як зараз: посилання, яке відкриває X з готовим текстом.

Секрети Telegram ті самі: `TG_BOT_TOKEN`, `TG_ADMIN_IDS`, `TG_REVIEW_CHAT_ID`, `TG_CHANNEL_ID`. Ключ API Worker і секрет вебхука виводяться з токена бота, окремо задавати не треба. Якщо колись змінити токен бота - просто знову запустити worker-deploy.

## Налаштування

- `worker/wrangler.toml` (`[vars]`): розмір вікна перевірки, прострочення, інтервал каналу, тихі години, `POST_TO_X` (`"false"` - лише канал), година підсумку, хештеги.
- `publisher.json` - аналітика: пороги (`min_score`, `min_money_uah`, `big_money_uah`), закономірності (`pattern_types`; `buyer_direct` вимкнено, бо для енергетики це норма), частка пошукових чернеток, військові/безпекові (`include_military`, `include_security` - зараз вимкнено), `rank_by_model` - порядок показу за прогнозом моделі замість суми під ризиком.

Перший запуск аналітики з нуля: Actions → prozorro-bot → Run workflow, `since` = дата днів 10 тому, `limit` = 40000. Потім ще раз з порожнім `since`, поки в лозі є "досягнуто max_tenders_per_run".

## Закономірності і пошукові випадки

Крім окремих тендерів, бот шукає підозрілі закономірності, де може й не бути переплати (`prozorro_patterns.py`):

- один постачальник забирає більшість конкурентних закупівель замовника (за 180 днів)
- той самий постачальник отримав кілька допорогових закупівель одного предмета, які разом перевищують поріг (можливий поділ)
- замовник, у якого майже всі конкурентні тендери з однією пропозицією, хоча для таких процедур це зазвичай не більше половини

Приблизно кожна четверта нова чернетка - пошукова (🧪): випадок, який не пройшов звичайні фільтри. Це щоб модель вчилась і на тому, що зараз відсіюється. Ліміту на кількість чернеток немає.

## Історія постачальників

`prozorro_history.py` пам'ятає, хто що вигравав за 24 місяці (лише «постачальник + категорія CPV + місяць»). Великий договір (від 1 млн грн) отримує прапорець, якщо переможець не мав жодної перемоги за 24 місяці (`SUPPLIER_NO_HISTORY`), раніше не працював у цьому розділі CPV (`SUPPLIER_NEW_IN_DIVISION`) чи групі (`SUPPLIER_NEW_IN_CATEGORY`).

`SUPPLIER_NO_HISTORY` і `SUPPLIER_NEW_IN_CATEGORY` - допоміжні: самі чернетку не створюють (8 з 8 чернеток «без історії» я відхилив), але видні в тексті й контексті.

Стан дозавантаження: `python prozorro_history.py status`.

## Модель

`prozorro_model.py` вчиться на моїх ✅/❌ і передбачає, чи схвалю я чернетку. Вона нічого не відсіює, лише:

- показує в кожній чернетці «🤖 Шанс схвалення (модель): N%»;
- визначає порядок, у якому чернетки приходять у чат (`"rank_by_model": true` у `publisher.json`): спершу ймовірні ✅, при рівних шансах - більша сума під ризиком. Черга перераховується щопроходу.

Прогрес і контроль якості (усе в гілці `bot-state`, тека `state/`):

- `decisions.jsonl` - знімок ознак кожного рішення (база тендерів чиститься, а це лишається)
- `shadow.jsonl` - прогноз для кожної чернетки, зроблений до мого рішення: найчесніша оцінка
- `model.json` - поточна модель; `model_history.jsonl` - якість після кожного навчання
- `checkpoints/` - знімок моделі щоразу, коли вона досягає нового найкращого результату (AUC перехресної перевірки)
- `model_report.json` - найкращий знімок проти поточної моделі на рішеннях, ухвалених після знімка (їх не бачила жодна). Якщо поточна гірша більш ніж на 0,05 AUC (на 20+ рішеннях), порядок визначає знімок, а мені приходить попередження в Telegram.

Команда `/model` у Telegram показує цей звіт.

## Діагностика

- `python -m prozorro.pipeline health` - стан Worker і вебхука (потрібен `TG_BOT_TOKEN` у `.env`).
- Журнал подій Worker (кожне натискання, команда й помилка, 60 днів): Actions → **worker-events** → Run workflow.
- Якщо прохід prozorro-bot впаде, в Telegram прийде повідомлення з посиланням на лог.
- `python -m prozorro.pipeline --db state/prozorro.db preview` - тексти для найновіших кандидатів без надсилання.

## Тести

- `python -m pytest tests` - тексти й перенесення журналу.
- `worker/test/run.sh` - наскрізний тест Worker локально (потрібен Node і `npx wrangler`): імітація Telegram, кнопки, вікно, канал, API. `X=1 worker/test/run.sh` - те саме для публікації в X через API.

## Дрібниці

- Військові та безпекові закупівлі (ЗСУ, НГУ, поліція, СБУ тощо) поки повністю вимкнені. Якщо колись увімкнути військові, вони анонімізуються і виходять із затримкою 14 днів.
- ФОП у постах не називаю (це приватні особи), у пості є тільки ЄДРПОУ юросіб.
- GitHub запускає cron із запізненням 5-20 хв, це нормально; основний розклад - cron-job.org.
- У публічному репо GitHub вимикає розклад (`schedule`) після 60 днів без комітів у main. Основний розклад - cron-job.org (запуск вручну через API), його це не стосується.
- Пороги в коді варто звірити з чинними правилами (воєнний стан).
